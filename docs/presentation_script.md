# Issue 相似性分析 Skill — 技术讲解稿

---

## 一、开场：为什么要做这个项目？

大家好，今天我要分享的是一个 **Issue 相似性分析 Skill** 项目。

做过开源项目维护的同学应该都有这样的体验：当仓库积累了大量 Issue 之后，新来的用户提了一个问题，其实历史上早就有人遇到过、讨论过、甚至已经解决了。但维护者很难凭记忆找到它——只能靠关键词搜索、翻标签、逐条看，效率很低。

**这个项目的目标就是：当新 Issue 进来时，自动从历史 Issue 中找到语义最相似的问题，并把相似问题列表和历史解决方案以评论的形式回复到 Issue 下面。** 同时还能基于历史已解决的 Issue 自动生成 FAQ 文档。

它的定位是一个 **AI Agent Skill**——不是一个需要部署和维护的独立服务，而是一组脚本和配置文件，Agent 通过自然语言指令直接调用。

---

## 二、整体架构

项目分为三层：

```
Agent / 用户（自然语言）
        ↓ 意图识别
   scripts/（执行层）  ← 8 个独立脚本，每个对应一类用户意图
        ↓ 调用
   issue_kb/（核心层） ← 9 个 Python 模块，纯业务逻辑
        ↓ 读写
   本地文件 + GitCode API
```

**关键设计原则：无服务化、无数据库依赖。** 所有数据都落在本地文件目录里，JSON 格式，人可以打开看、可以版本管理、可以备份。Embedding 向量也缓存在本地，构建一次、多次复用，避免重复计费。

## 三、核心技术点

### 3.1 相似性引擎 — Embedding + 余弦相似度

这是整个系统的核心能力。流程很简单：

1. **文本构建**：把 Issue 的标题（重复两次加权）、正文、标签、解决方案、前 3 条评论摘要拼接成一段文本
2. **向量化**：调用 OpenAI 兼容的 Embedding API（text-embedding-3-small），生成 1536 维向量
3. **索引缓存**：向量以 `{issue_number: vector}` 的形式缓存在 `embeddings.json`
4. **搜索**：计算查询向量与索引中所有向量的余弦相似度，按分数排序取 Top-K

为什么没用 ChromaDB、FAISS 这些专业向量库？因为我们的知识库规模在 **千级**（当前 517 条），全量遍历毫无性能压力——实测平均查询耗时 **0.31 秒**。用 numpy 手写的余弦相似度就足够了，简单可靠，零额外依赖。

**容错设计值得一提：**

- 按批调用 API（10 条/批），**每批成功立即落盘**，中断后重跑只补未完成部分
- 单批失败不中断整体流程，最后统一重试一轮
- 长文本在 6000 字符处截断（模型上限 8192 token），标题重复加权保证永远不会被截断到

### 3.2 模板噪声清洗 — 频率预筛 + LLM 语义判定

这是项目中我认为**最精巧的设计之一**。

GitCode 仓库的 Issue 普遍携带固定模板。其中有两种高频内容：
- **无意义噪声**："欢迎加入社区"、"提交前请搜索"、"安全信息提醒"等——跟具体问题无关，但会人为抬高相似度基线
- **有意义的结构骨架**："### 🐛 问题描述"、"### 环境信息"等——同样是高频行，但有助于阅读

纯频率统计无法区分这两种——高频可能是噪声，也可能是好内容。

我们的混合策略是：
1. **频率只负责预筛候选**：一行出现在 ≥ 3 条 Issue 中，才送 LLM 判定。只出现一次的用户独特内容天然保留
2. **remove/keep 最终判定 100% 由 LLM 语义决定**：给 LLM 正负例锚定标准，逐行给出 verdict 和 reason
3. **判定结果持久化为 `llm_template_cache.json`**：人可读、可编辑。手改后 `--apply` 即可重落地
4. **LLM 失败降级为保留**，绝不误删用户内容

实测结果：182 行高频行被判定，41 行 remove（客套话/须知/安全提醒）、141 行 keep（结构标题/用户内容），**零误杀**。清洗后 Issue 的平均噪声占比从 24% 降到接近 0。

### 3.3 FAQ 自动生成 — 聚类 + 中英双语

从知识库中筛选已解决的 Issue，按分类分组，组内用 Embedding 相似度做贪心聚类（阈值 0.85），避免同类问题重复生成 FAQ。

每条 FAQ 调用一次 LLM，**同时产出中英文字段**，中文写入 `docs/faq/zh/`、英文写入 `docs/faq/en/`。

**降级兜底**：没配 LLM 或调用失败时，回退纯中文模板，跳过英文文档——不产生半成品。

默认生成**草稿**（文件名带 `_draft`），维护者确认后去掉后缀发布。

### 3.4 增量维护 — 游标 + 断点续跑

知识库不是一次性产物，需要持续同步。增量机制用**双保险**：
- **时间游标**：记录上次同步到的时间点，下次只拉取此后更新的 Issue
- **已处理集合**：即使游标出问题，也不会重复处理和评论

评论防重复用的是 HTML 注释标记 `<!-- issue-skill-scan-report:v1 -->`——对用户不可见，发布前检查已有评论中是否存在该标记。

## 四、效果数据

我们在 517 条 Issue 的知识库上做了检索效果测试：

| 指标 | 数值 |
|------|------|
| 阈值命中率（Top-1 ≥ 0.75） | **52.9%** |
| 平均 Top-1 相似度 | **0.7549** |
| 标签重合率 | **91.8%** |
| 查询成功率 | **100%**（51/51） |
| 平均查询耗时 | **0.31s** |

未命中的 47% 主要是 RFC/Feature 首次提案——"前所未有"的新问题检索不到相似问题是**预期行为**，恰恰说明系统在正确工作。

高分案例中，#525 和 #533 互为最佳匹配（0.884），它们分别是"CCA 新增 LLC Cache 解析"和"CCA 新增 Thread State 解析"——确实是同系列的 Feature。

## 五、设计决策背后的思考

| 决策 | 选择 | 为什么 |
|------|------|--------|
| 交付形态 | Skill 脚本目录 | Agent 直接调用，无需部署服务、无需运维 |
| 存储方案 | 文件型 JSON | 无数据库依赖，可查看、可 Git 管理、可备份 |
| 向量检索 | numpy 全量遍历 | 千级规模下简单可靠，不引入额外依赖 |
| 模板清洗 | 频率预筛 + LLM 判定 | 纯频率分不清好坏，纯 LLM 成本太高，混合最优 |
| 双语 FAQ | LLM 一次调用产双语 | 成本减半，语义一致性有保障 |
| 评论防重复 | HTML 注释标记 | 对用户不可见，跨运行稳定 |
| 容错策略 | 单条失败跳过，批次级落盘 | 批量任务不因个别异常中断 |

## 六、Agent Skill 的使用方式

这个项目被设计为一个 **Skill 目录**，包含 `SKILL.md` 说明文件 + 可执行脚本 + 配置模板。

Agent 通过自然语言识别意图，映射到对应命令。比如：

- "扫描这个 Issue 看有没有类似问题" → `scan_issue --issue 123`
- "把这个 Issue 加入知识库" → `add_issue --issue 123`
- "每天定时扫描新 Issue 并评论" → 创建定时任务执行 `scan_new --mode comment`
- "基于历史 Issue 生成 FAQ" → `generate_faq`

支持任意 gitcode.com 仓库，通过 `--repo owner/repo` 指定。每个仓库拥有独立的知识库目录，互不干扰。

---

## 七、总结

这个项目的核心价值是：**用最低的部署成本（零服务、零数据库），实现了一个完整的 Issue 知识管理和相似性检索系统。**

几个关键技术亮点：

1. **Embedding + 余弦相似度**：简单有效，千级规模足够用
2. **频率预筛 + LLM 语义判定**的模板清洗策略：精确区分高频噪声和高频有价值内容
3. **批次级落盘 + 失败重试**的容错设计：中断可续跑，不浪费 API 调用
4. **中英双语 FAQ + 降级兜底**：有 LLM 就双语，没有就纯中文，不会产生半成品
5. **Agent Skill 形态**：无需部署，自然语言驱动，开箱即用
