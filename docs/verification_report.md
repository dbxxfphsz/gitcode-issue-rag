### 截断策略分析

**当前策略**：在 `_get_embeddings_api()` 入口处对所有文本硬截断至 6000 字符。

**截断后 token 安全性验证**（以最长 Issue #308 为例）：

| 指标                                 | 值                                        |
| ------------------------------------ | ----------------------------------------- |
| 原文 body                            | 24,677 字符（中文 6,144 + 非中文 18,533） |
| 截断后 embedding 文本                | 6,000 字符                                |
| 截断后估算 token（保守：中文 2t/字） | ~4,464 tokens                             |
| 截断后估算 token（宽松：中文 1t/字） | ~2,760 tokens                             |
| 模型上限                             | 8,191 tokens                              |
| 安全余量                             | **3,727+ tokens**                         |

**对检索质量的影响**：

- 被截断的 25 条 Issue 绝大多数为 **RFC/Feature 设计文档**，body 包含大量代码块、表格、方案设计细节
- `_build_issue_text()` 将标题重复两次置于最前，确保**标题永远不被截断**
- 对于主题级相似匹配，标题 + 前段正文已包含足够的语义信息
- 截断丢失的主要是 RFC 中后段的实现细节和代码示例，对"是否是同一类问题"的判断影响极小

### 风险评估

| 风险项          | 等级       | 说明                                                    |
| --------------- | ---------- | ------------------------------------------------------- |
| API 调用失败    | **无风险** | 6000 字符截断后 token 远低于 8191 上限                  |
| 批量连带失败    | **无风险** | 截断在 API 入口统一执行，不会有漏网之鱼                 |
| 检索质量下降    | **低风险** | 仅影响 25 条长 RFC 的尾部信息，标题权重加倍保障主题匹配 |
| 未来 Issue 超限 | **低风险** | 新 RFC 可能更长，但截断策略是兜底保护，与原文长度无关   |

## Q2: 模板噪声清洗是否生效？对检索准确性有何影响？

### 结论

| 指标                 | 状态                                                                               |
| -------------------- | ---------------------------------------------------------------------------------- |
| 清洗逻辑是否存在     | **是** — `issue_kb/template_classifier.py` 实现了完整的频率预筛 + LLM 语义判定流程 |
| LLM 判定缓存是否生成 | **是** — `llm_template_cache.json` 含 182 行判定（41 remove / 141 keep）           |
| 缓存覆盖率           | **100%** — 所有高频行（≥3次出现）均已被 LLM 判定，无缺口                           |
| 是否已应用到知识库   | **否** — 517 条 Issue 中 0 条含 `body_raw` 字段，清洗从未落地                      |
| 对 embedding 的影响  | **显著** — 平均 24% 的 embedding 文本为模板噪声                                    |

### 问题发现

**`clean_templates.py --apply` 从未执行**，导致：

- `issues/*.json` 中 `body` 字段仍包含完整模板噪声
- `embeddings.json` 中的向量是基于**未清洗文本**生成的
- 所有 Issue 共享的模板噪声（提交须知、安全提醒、社区页脚）在向量空间中人为抬高了相似度基线

### 清洗逻辑验证

| 验证项                | 结果                                                              |
| --------------------- | ----------------------------------------------------------------- |
| 频率预筛覆盖          | 182/182 高频行已判定，**0 缺口**                                  |
| remove 判定准确性     | 41 行均为客套话/提交须知/安全提醒/空占位，**无误杀**              |
| keep 判定准确性       | 141 行包含结构标题/用户内容/RFC 章节，**保守正确**                |
| `clean_body()` 幂等性 | 清洗后再次清洗无变化，**通过**                                    |
| 查询侧对称清洗        | `scan_issue.py` 第 32 行对 target 做 `clean_body()`，**逻辑存在** |

### 风险评估

| 风险项            | 等级       | 说明                                                                             |
| ----------------- | ---------- | -------------------------------------------------------------------------------- |
| 相似度虚高        | **中风险** | 共享模板的 Issue 之间相似度被噪声抬高，可能导致不相关 Issue 超过阈值             |
| 短 Issue 语义稀释 | **高风险** | body < 300 字符的 Issue，噪声可占 40%+，有效语义信号被严重稀释                   |
| 长 Issue 影响     | **低风险** | RFC 类长文档本身语义丰富，20 字模板噪声影响可忽略                                |
| 查询侧不对称      | **中风险** | 扫描时 query 侧会做 `clean_body()`，但知识库侧向量是未清洗文本生成的，两侧不对称 |

### 修复建议

执行一次 `clean_templates.py --apply` 即可修复：

```bash
python -m scripts.clean_templates --apply
```

该命令会：

1. 按 LLM 缓存回填所有 Issue（`body_raw` 保留原文，`body` 存清洗后文本）
2. 基于清洗后 body 全量重建 embedding 索引
3. 预计影响 492/517 条 Issue，embedding 全部重算
